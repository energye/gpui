## 1. 三招核实（证据链）

### 第一招：印章只盖一次（已实锤）

- spin 图标 66x66 纹理只录一次：BoundaryRerecord=2（预热加首次），BoundarySkip=1188（10 秒 600 帧）。
- 拼包 Phase1 约 0.004ms 加 Phase2 约 0.009ms（实测 TexturedPhaseMs1/2，已撤出的临时观测值），不是瓶颈。
- 证据：ui/scene/textured.go pushRecordCTM 去旋转录制、合成走 live CTM；spin_min 日志 frame6 record local w=66 h=66 后逐帧 blit。

### 第二招：损伤剪刀没生效（已实锤缺口）

- GLES 交换链每次 BeginFrame 都 `CreateTextureView` 一个新 Go 对象（gpu/gwgpu/gles/swapchain.go:279），会话层 `view != s.lastView`（render/internal/gpu/render_session.go:5619/6100/6234）恒成立，frameRendered 恒 false，fullSurface 恒 true，损伤剪刀分支走不到。
- webgpu 同理：GetCurrentTexture 逐帧新包装（gpu/webgpu/surface.go），NativeHandle 回 0（gpu/webgpu/texture.go），没有可比的稳定身份。
- 后果：指标写 damage_union，实际每帧整面合成加整面提交。8281px 损伤算出来了但提交没用上。

### 第三招：损伤要并历史（已实锤缺口，Flutter 有标准做法）

- 交换链图片轮转，当前这张上次展示是几帧前，只画当前帧损伤会漏旧位置（白圈就是这么来的）。
- Flutter/GLFW 标准做法：查 EGL_BUFFER_AGE，无扩展按 4 处理，并最近 age-1 帧损伤（engine/src/flutter/examples/glfw_drm/FlutterEmbedderGLFW.cc:222-247）；embedder 侧 populate_existing_damage，部分提交关不掉就退整面（embedder.cc:390-406）。
- 本仓现状：render 层无损伤历史，无 buffer-age 查询，无 per-image 帧状态。grep damageHistory/damageForPlan/ClearDamageHistory 全空。

## 2. 真方案（对齐项）

1. 视图稳定身份：比父纹理或原生句柄，不比 Go 包装指针。GLES 用 GL 纹理 id（resource.go NativeHandle），webgpu 找稳定句柄，找不到就保持整面（诚实回退）。
2. 损伤并历史：记最近 4 帧损伤（轮转一般 3 到 4 张，取 4 兜底），提交用并集；重配/尺寸变清历史加整帧。
3. 上屏透脏区：render 调 EndFrameWithDamage，GLES 接已有 SwapBuffersWithDamage（queue_linux.go 已写好，一直传 nil），webgpu 保持整面回退。

## 4. 第二档调研结论（只读代码，未动手）

- 每帧固定动作：编码器新建（blit 走 sessionBlitEncoderDesc）、渲染通道开关、提交一次、换图一次。60 帧下这四件套省不掉。
- 命令缓冲两家都是一次性的：webgpu 提交后标记 submitted 再交就报错，GLES 提交时把命令列表清空回收了。所以“编一次投多次”两边都不支持，要做就得另起机制，不是顺手改。
- 已经省掉的部分：uniform slab 只有宽高和透明度变了才上传（spin 这扇窗基本不传）；绑定组按槽位缓存，纹理和采样器不变就不建；顶点上传带哈希比对，不变不传。这三块前人已经做过。
- 每帧还在变的东西只有一件：旋转把四个角坐标烘进顶点里了，所以顶点每帧重算加上传（两张四边形，一共 12 个点，量很小）。
- PresentCount 是帧数的两倍只是计数口径（循环里记一次、结果里再记一次），真实提交一帧一次（FrameFlushes 恒 1），不用管。
- 结论：第二档真要动手，方向是把旋转从顶点里拿出来改成参量传（着色器里转），顶点一次上传后面只比哈希；再往下就是提交本身的固定开销，那是驱动的事，省不了。预期收益小（个位数），风险在 render 加 gpu，要全回归。

## 5. 第二档设计（已核实，未动手）

- 放哪：旋转只进 uniform 矩阵，顶点只发轴对齐四边形。着色器里 `transform` 矩阵槽是现成的，现在只写了正交投影，旋转直接乘进去就行，不改顶点格式，不管线布局。
- 比对键：uniform 跳过上传只比宽高透明度（两条路共用 `imageUniformLastKey`），角度必须进键，不然角度冻住。顶点哈希比对不动：轴对齐顶点静止后自动命中，上传跳过。
- 合并：`canMerge*` 都不看角落，旋转走 uniform 不影响合批。
- 命令缓冲两家都是一次性，复投等于重录，不做。
- 损伤、剪刀、上屏逻辑都不动：损伤还是按包围盒在 CPU 算，PresentCount 双计数只是 metrics 口径问题。
- 预期：个位数收益（省 12 个顶点重算加一次小上传）；提交固定开销（编码器、提交、换图）还在，60fps 底线不动。风险：render 加 gpu 双后端一次改到位，全回归加像素对比。

## 7. 每帧 GL 调用清单（2026-10-16 实测，光栅线程）

同二进制两轮稳态（t=2..15s 稳定）：固定 14 次 FFI/帧（840 次/s），全部落在光栅线程；每帧驱动内时间合计约 334µs ≈ 2.0pt 单核（FFI 计时口径，含驱动的 C 内时间）。命令序（17 条命令，状态缓存并掉约 3 条）：BindVAO → BindSurfaceFramebuffer → SetViewport → DrawBuffers → Scissor(195,115,89×89) → BindGroup → VertexBuffer → UseProgram → PipelineState → 6 顶点 Draw → 6 顶点 Draw → blit → swap。

| 调用 | 次/帧 | 单次（µs） | 备注 |
|---|---|---|---|
| eglSwapBuffersWithDamageKHR | 1 | 105~115 | 上屏，最大单项 |
| glBindFramebuffer | 2 | 34~44 | 渲染通道绑定 + blit 前切缓冲 |
| glBlitFramebuffer | 1 | 30~42 | 损伤 blit 到窗口默认帧缓冲 |
| glDrawArrays | 2 | 19~24 | 两张 6 顶点四边形 |
| glBufferSubData | 2 | 13 | 小上传（非顶点：顶点已静止命中） |
| glBindBufferRange | 2 | 4~5 | uniform 绑 |
| glScissor | 2 | ~4 | 损伤剪刀（常驻已撤回，见修订表） |
| glBindTexture | 2 | 3.5 | 纹理绑定 |

- 稳态无 glClear、无 glGetError、无 fence 查询；glGetError/着色器类调用只在启动 t=1s 出现。
- 剪刀常驻已于 2026-10-16 撤回（依据不足+前提证伪）：稳态恢复每帧 1 次 glEnable + 1 次 glDisable，上表 14 次/帧为常驻下的计数，撤回后约 16 次/帧；固定命令 15s 三轮 7.28/7.07/7.31%，同小时 A/B 常驻 7.16/7.21/7.44%（中位差 +0.07pt，噪声内）。
- uniform 合并上传：对本窗收益 ≈ 0。uniform 全链 glBufferSubData×2 + glBindBufferRange×2 约 35µs/帧 ≈ 0.2pt；就算合并成一次上传/一次绑定，上限也只有约 0.1pt。
- 唯一属于我们的结构开销：blit（30~42µs）+ 一次 FBO 绑定（34~44µs）+ blit 剪刀设置，合计 70~90µs/帧 ≈ 0.45~0.55pt。**已于 2026-10-16 落地**：GLES 面 pass 直渲窗口默认帧缓冲（上屏只调 eglSwapBuffers[WithDamage]），做法与依据见 §6 首行；上表 14 次/帧是离屏路下的计数，直渲路少了那条 `glBlitFramebuffer` 与 blit 前的 `glBindFramebuffer`（稳态降到约 12 次/帧），要精确数字再挂一次 FFI 计时探针重测。
- 其余（swap、draw、bind 的驱动侧时间）是驱动固有成本，§4 结论不变。线程账另见修订表：光栅 2.65% + sysmon 1.72% + 事件循环 0.80%。

### 8.4 结论与杠杆

1. **Go 侧没有剩下的大洞**：FFI 机制 0.02pt；自家 `ui/*` 全在 1.9% 以下（最大单项 `ui/rendering.appendNode(-Inner)` 各 2%）；GC/分配 ≈0.3pt；自家 `gettid`/`getpid` ≈3.6 次/帧属噪声级。
2. **与尺子的差（0.73~1.4pt）构成就是两笔机制费**：Go 运行时线程交接（gosched 0.53pt + futex 0.42pt + 调度器内部 0.2~0.3pt ≈ **1.0~1.2pt**）+ 每帧 vblank 请求/事件读那一趟（**≈0.4pt**）。驱动 C 侧 ≈1.1pt 与尺子同类（glxgears 的 swap+draw+X 事件循环也在它自己的 3.0~3.3pt 里）。
3. **没有可搬去 GPU 的账**：像素不在 CPU（`CPUFallbackOps:0`、`GPUFallbacks:0`），旋转已是 GPU 变换（`gpuTex` uniform 矩阵 / 合成路 live CTM，§5 已落地）；命令编码与损伤计算 Flutter/Impeller 同样在 CPU 做。
4. **剩余杠杆（按证据排序，收益按 profile 绝对毫秒反推）**：
   - ⑴ 事件循环等待改走 Go netpoller，拆掉 `yieldBeforeBlockingPoll` 与其交接（**§8.5 隔离实测更正：只换 park、保留 8ms 切片净收益 ≤0.2pt，原估 0.3~0.5pt 作废；park 的价值在解锁「去切片」**；动 `ui/platform` X11/Wayland 事件循环，可能带 `ui/scheduler`）。
   - ⑵ vblank 通知驱动（X11 Present 通知；本机缺 `libXpresent.so.1`，需自补 XCB-Present 选择段）替掉每帧 DRM 请求+读与监听 goroutine（目标 0.3~0.4pt；动同层 X11 事件流，高风险）。
   - ⑶ 每帧睡眠/唤醒次数 3.4→1（Host 等待 2.3→1 次/帧，present/acquire 握手合并；**机制与更正见 §8.5：每条 ~70µs 记账费，目标 0.5~0.9pt**；动 `ui/embedder`+`ui/platform`，先以 8ms 切片单点 A/B 判定）。
   - ⑷ 分配池化（命令缓冲 / 参数 `[]uintptr` / 事件切片复用；上限 0.3pt，低风险；动 `gpu/gwgpu/gles` + `render`）。
   - ⑸ 合并两次 `glDrawArrays`（两张四边形一次画，~0.12pt；动 render 合批）。
   - 说明：⑴⑵⑶ 都属结构性改造、都在高风险区，动手前另作影响面评估并请示；⑷⑸ 是通用优化但收益小。

**② 睡眠时长扫描（`Nanosleep`）**：2/4/8/16/32ms → 74.2/80.3/83.5/90.3/100.4µs ⇒ **≈72µs 固定 + ≈0.9µs/ms**（单次运行间抖动 ±3µs）。8ms 切片 ≈83µs、整帧 16.6ms ≈88µs ⇒ 少睡一次省的是那份固定费，跟睡多久几乎无关。

**③ 那第五刀的 park 为什么赢 1.29pt**——换的是「抱着 P 长阻塞」这一档，不是单循环价格：旧写法让 goroutine 在 `_Psyscall` 里停满 16.6ms，sysmon 每 10ms retake（`runtime/proc.go` retake→handoffp）并把 sysmon 拉回 20µs 空转循环；当天实测 4.67% 对 3.38%，其中 **sysmon 一项 1.70%→0.20%（1.5pt）**。同族证据：第二刀 A/B（不切片 pristine 8.70/8.96% 对切片 8.11~8.50%）⇒ **长 P 持有等待的风暴 ≈1.1~1.3pt/次，比它省下的睡眠值钱**，这正是 `maxHostWait=8ms`（`ui/embedder/pipeline_app.go:93`，注释在 85-92 行）的由来。**推论：机制（raw 阻塞 ↔ park）与切片（8ms 切片 ↔ 不切片）必须成对改，两种混合组合都已被实测证伪。**

**④ 每帧睡眠/唤醒次数（本账的真实来源）**

- 本窗（`spin_min` 15.079s / 899 帧 / 904 presents / 59.95fps、`MissedVSync 0`、`PresentMode damage_union`、`DamageAreaPx 7921`、该轮 `CPUPctAvg 5.17%`）`WaitCensus`：`Host{Count 2134, Over1Ms 2073, MaxMs 8.52}`＝**2.37 次/帧**、`Vblank{Count 898, 全部 Over1Ms, MaxMs 32.07}`＝0.99、`Present{Count 899, Over1Ms 2, MaxMs 1.49}`、`Acquire{Count 899, MaxMs 0.047}` ⇒ **真正的阻塞睡眠 ≈3.4 次/帧**（Host 2.37 + Vblank 1.00；Present/Acquire 不阻塞）。
- `Present` 只有 2 次 >1ms、最大 1.49ms ⇒ 非阻塞交换后 swap **不等** vblank：§8.1 的 141µs/帧是驱动真在 swap 时做掉本帧 GL 工作的 CPU（Mesa 把帧内 GL 工作推迟到 swap 时做），不是等待，也没有可搬 GPU 的账。
- 尺子（本轮新测法：`strace -f -T` 按调用时长筛）：`glxgears 480×320` 16s 窗内 **≥10ms 的 `poll` 923 次（合计 12.53s）**，同窗 896 帧（296+300+300）⇒ **1.03 次/帧**；**全程 0 次 nanosleep、futex 仅 78 次**（10162 次 poll 里其余约 9200 次是 XPending 式零超时轮询）⇒ 标准的形状就是**一帧一次阻塞等待**。

**⑤ 为什么是 2.37 次/帧，以及常量与刷新率的关系**

`maxHostWait = 8ms` 是**绝对常量**（`ui/embedder/pipeline_app.go:93`；理由＝把每次阻塞压在 Go runtime 10ms syscall-retake 阈值之下，与显示器无关），而帧长是**随刷新率自适应**的：`seedRefreshFromHost()`（`pipeline_app.go:923`）从 `platform.DisplayRefreshReporter` 播种（20~240Hz 门），`ui/scheduler/scheduler.go:40 DefaultAnimTick = 16ms` 只是没上报时的兜底，`:155 boundaryPeriodLocked()` 用学到的真实边界周期（`:46 vsyncFreshWindow` 2 tick 抖动窗），`:175 clampPeriod` 下限 0.8×参考周期与 4ms 绝对地板。`WaitTimeout()`（`:617`）本已算出「到下一个帧边界的剩余时间」（`nextFrameBoundaryLocked`），却在 `pipeline_app.go:1190-1191` 被 8ms 常量切碎：

| 刷新率 | 帧长 | 切片后 Host 等待/帧 | 实测 |
|---|---|---|---|
| 60Hz | 16.68ms | 2~3（14~16ms 剩余 ÷ 8ms） | **2.37（本次）** |
| 120Hz | 8.33ms | ≈1.04 | 未实测 |
| 144Hz | 6.94ms | 1（常量失效，不再切） | 未实测 |

⇒ 每条睡眠的 ~72µs 固定费是**每次事件**的、与刷新率无关；所以「少睡几次」省下的是 `(次数−1) × ~72µs` **每帧绝对值**，在高刷下**每帧占比翻倍**（每秒帧数翻倍）⇒ **今天的设计对 60Hz 屏收的税比 120Hz 重一倍。**

**⑥ 结论与下一步**

1. 「甲」按原口径（只把 park 换进来、保留 8ms 切片）**不值得做**：净收益 ≤0.2pt，且按 ① 可能为负。
2. 真杠杆＝**每帧 3.4 → ~1 次阻塞等待**：主循环一次 park 到帧边界（不再切片，`maxHostWait` 退场），把 vblank 那次等待合并进来（今天 vblank 监听 goroutine 与主循环的软件 deadline 在等同一个沿）。按 ① 的 83~90µs/循环算，砍掉 2.4 次 ≈ **0.17~0.22ms/帧 ≈ 1.0~1.3pt（上限）**；同小时实测总缺口 0.73~1.06pt ⇒ 该杠杆量级能兜住整个剩余缺口。Go 侧那几笔（`goschedImpl` 0.53pt + `futex` 0.42pt + 调度器内部 0.2~0.3pt）是**同一批循环从 Go 侧看的样子，不可与内核记账相加**。
3. **顺序不可倒**：去切片必须已有 park（否则重演 ③ 的风暴）；而 park 要看 X fd 必须走代理——`internal/poll.FD.Init` 会对**共享 file description** 打 `O_NONBLOCK`（`dup` 共享同一 description，不是独立的），会打断 libX11 的阻塞读 ⇒ 需要 (a) 一个只做「短切片 poll X fd → 写 wake pipe」的代理 goroutine（或主循环只 park wake pipe + 定时器），(b) 拆卸握手（Wayland `Surface.Destroy` 自锁是同类坑的前车之鉴），(c) Wayland 同改同验（`ui/platform/wayland_linux.go:1661`/`:1718` 同一写法）。
4. **下一步建议**：先做**单常量 A/B**（`maxHostWait` 8ms → 帧边界，只动一处常量、可回滚），用同小时配对台架看三件事——`WaitCensus.Host.Count` 是否 2.37→~1.05、进程 CPU 是否降、retake 风暴是否回来（按 ③ 预测会回来；若风暴吃掉的比省下的多，即坐实「park 是去切片的前置条件」，随即进 甲′2）。改动面都在 `ui/embedder`/`ui/platform`（低风险层），不碰 render/gpu。**（本轮已做：结果见 §8.6——去切片单独做输 1.83~2.43pt，风暴回来，park 是硬前置。）**

### 8.6 甲′1 单常量 A/B 实测：去切片（不改机制）输 1.8~2.4pt（2026-10-17，主树未改）

做法：只删 `ui/embedder/pipeline_app.go:1189-1192` 的 8ms 切片块（其余一行不动；`maxHostWait` 常量与其注释留着），在临时 worktree `/tmp/gpui-noslice`（基点 c3d875d3）构建 `spin_noslice`，与主树 HEAD 构建的 `spin_slice8` 同小时 ABBA 交替（B A A B，第 4 轮撞上既有开窗偶发失败：wall 0.00s / threads 0，故同臂补跑），臂别、命令、`-auto-only`、480×320 全同；CPU 取 schedstat 求和（jiffies 对照同档），风暴看 per-tid `sched/s` 与阻塞点直方图。

**三条结论**：
1. **去切片单独做，输 1.83~2.43pt**：省下 0.88 次睡眠/帧只值约 0.4pt（按 §8.5 每循环 ≈72µs 固定费），换来的是每次 >10ms 的 P 持有等待触发 sysmon retake 空转——**一笔 2.36~2.62pt 的风暴**（单条 tid、以 sys 时间为主），净亏与实测一致；同小时尺子 2.64~2.87% 说明背景没有整体漂移，差值就是这个机制差。
2. **§8.5 ③ 的「风暴 ≈1.1~1.3pt/次」按本轮更正为「随持有长度与频率放大」**：本轮是每帧一次 ≈17ms 持有 ⇒ 2.4pt；第五刀那次（16.6ms/帧的 ioctl）1.29pt、第二刀反推 1.1pt。机制同一档，价格取决于每次抱多久、每帧抱几次。
3. **`park` 是去切片的硬前置（已由 A/B 钉死，不再是推测）**：只要等待还是 raw `poll`（抱着 P），8ms 切片就不能去；要拿那 ~1.0pt 只能走 甲′2。另外 A 臂 Host 等待只降到 1.49 次/帧（不是 1.0）——因为 vblank 那次等待仍独立存在，**合并它是 甲′2 的另一半**。
4. 两臂功能与帧率都不缩水（903~905 presents / 15.1~15.2s、60fps、`MissedVSync 0`、AvgFrame 16.69ms）⇒ 这不是「拿功能换 CPU」的取舍，纯粹是等待机制的账。
5. 口径附注（指标诚实性）：示例自报的 `cpu=`（`CPUPctAvg`，含启动期摊薄，本轮 B 臂 4.78~6.59%、A 臂 7.57~8.15%）**不能用于臂间比**——绝对值含启动一次性开销，方向虽一致但量被放大；臂间比一律用同窗外部 schedstat/jiffies 配对法。
